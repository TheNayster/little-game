24 September 2026. Bounded Windows-only follow-up for **ITEM-02 / TRAVEL-01**. G1/G2 mobile and child acceptance remain open.

## What changed

The checkpoint reader used File.Exists, which returns false for a directory and can suppress access errors. A regression test reproduced a directory at the save-file path being classified as Missing. The reader now queries file attributes, treats only missing-path exceptions as Missing, and propagates directory/access failures. A blocked save cannot silently become a blank world or roll back to an older backup just because the latest file cannot be read.

Windows verification arguments now fail closed. Supplying an invalid test namespace exits before opening normal saved play. Build metadata advertises verification contract 2 so the hard-stop wrapper refuses older players that lack this behavior.

## Observed checks

- [Before the fix](evidence/solo-recovery-2026-09-24/rules-before.json): the directory-at-save regression failed. [After](evidence/solo-recovery-2026-09-24/rules-after.json): all **20 core tests passed**, including a primary save exclusively locked while an older valid backup exists.
- Fresh non-development Windows **39** passed [native OS-termination recovery](evidence/solo-recovery-2026-09-24/crash-result.json). The test saved an orange avatar, position, activity, grown flower, full bucket and partly cleaned puddle while a pointer held the bucket. The wrapper killed only its own process. No OnApplicationQuit marker was written. The checkpoint still contained the hold after termination.
- Reopening restored the **exact complete checkpoint state**, except the deliberate release of the transient hold and its revision increment. The bucket could then be picked up and dropped again. [Reopen](evidence/solo-recovery-2026-09-24/crash-resume.json).
- A directory at the primary path and an exclusively locked primary both stopped the native game's load path. Primary/backup progress was preserved. The blocked JSON's default LoadedStatus field says Missing because the read threw before assigning it; the explicit loadBlocked flag and error identify the actual result. [Directory](evidence/solo-recovery-2026-09-24/directory-at-save.json), [locked primary](evidence/solo-recovery-2026-09-24/locked-primary.json).
- Windows **37 → 39** retained seeded play and recovered a deliberately truncated primary using the prior good checkpoint. [Update](evidence/solo-recovery-2026-09-24/update-39.json), [recovery](evidence/solo-recovery-2026-09-24/recover-39.json). Full input, cancellation, narration and 1280×960 layout checks passed again: [input](evidence/solo-recovery-2026-09-24/input-39.json).

The force-stop test establishes recovery of the last successfully written checkpoint. It is not a power-loss test, a guarantee that unsaved in-memory actions survive, or physical iPad lifecycle evidence. No Mac, phone or tablet was accessed. All injected faults stayed inside fresh GUID test folders; normal preview progress was untouched.

## Repeat

With a fresh Windows build advertising verification contract 2, run `Tools/Test-SoloCrash.ps1 -BuildNumber N`. It verifies artifact hashes, creates isolated storage, validates the waiting player's identity, kills the returned process object, relaunches and checks the state. It then exercises the directory/locked-file barriers without deleting the preserved test data. Results remain under ignored LocalData/Verification, with compact evidence copied here.

The prepared iPad export 38 predates this reader fix. It must be refreshed before the next device qualification; exporting on Windows does not require contacting the Mac.
