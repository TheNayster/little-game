# G3 — keeping the other players connected when someone leaves

24 September 2026. **Fixed and qualified on Windows shared build 68; the two-window preview is updated with its exact saved world preserved.** This bounded task follows the movement work and covers **FAMILY-01, JOIN-01, WORLD-01/02 and ITEM-02**. Windows qualification is recorded below; automatic discovery, automatic reconnect and iPad host migration remain required implementation work.

## What failed, and what we verified

The returning player was waiting for their first snapshot, but the problem began earlier: the Windows server stopped receiving traffic after a client process was killed. The other clients eventually timed out too. The process, socket and game loop were still running. This was not just a slow initial world download.

Unmodified build 63 reproduced the failure. Instrumented **65**, still using registry Unity Transport **2.7.4**, reproduced it again. The server reported a created, bound, listening driver, no receive error, and a maximum measured frame gap of **29.5 ms**, but no incoming data for **35.19 seconds**. These observations narrow the problem; they do not identify a particular Windows native socket error. [63 failure](evidence/rejoin-recovery-2026-09-24/baseline-network-63.json), [65 failure](evidence/rejoin-recovery-2026-09-24/baseline-network-65.json), [connection trace](evidence/rejoin-recovery-2026-09-24/baseline-connections-65.json).

The installed transport source revealed a receive-buffer ownership leak. Scheduling a receive acquires a buffer. The receive-completion loop discarded failed, empty or oversized completions without releasing their buffers. Successful completions go through the packet queue and are released later. Discarded completions never take that path, so they can exhaust the pool even while the socket remains valid.

A fresh isolated test sent **1,024 empty and 1,024 oversized UDP datagrams** to its own loopback server, then requested fresh actions from each of four clients. Registry build 65 stopped acknowledging commands; patched **66** kept all four responsive. The same patched build then passed eight rotating hard-kill/rejoin cycles. That is direct before/after evidence for this discard-path fault. A specific native error such as `WSAECONNRESET` was **not captured**, and should not be presented as a measured cause. [Unpatched discard failure](evidence/rejoin-recovery-2026-09-24/baseline-discard-65.json), [patched discard and crash cycles](evidence/rejoin-recovery-2026-09-24/receive-resilience-66.json).

## Source review and the local package change

- A report in Unity's own NGO issue tracker describes the same Windows pattern: force-killing a remote process leaves the server alive but unable to receive, and the remaining clients time out. It is **closed as not planned**, with stale closure activity; that status is not an upstream fix or confirmation of our diagnosis. Our local reproduction and code inspection provide the evidence for this game's change. [Unity issue 4096](https://github.com/Unity-Technologies/com.unity.netcode.gameobjects/issues/4096).
- The public Unity package registry identified **2.7.4** as the latest available transport version during this review. The changelog did not identify a newer released fix for this leak. We therefore embedded the pinned package with a minimal local change, rather than claiming a vendor update solved it. [Unity registry](https://packages.unity.com/com.unity.transport), [official transport changelog](https://docs.unity3d.com/Packages/com.unity.transport@2.7/changelog/CHANGELOG.html).
- Source inspection used the actual package installed in this project: `Runtime/UDPNetworkInterface.cs` and `Runtime/PacketsQueue.cs`. The public 2.7.4 package archive was also downloaded and checked against its registry hash. Only the completed discard paths release a buffer in the patch. Pending receives and successful packets retain their original ownership rules.

The project now uses **Unity Transport 2.7.4 with local embedded patch 1**, with NGO still pinned to **2.13.2** and Unity **6000.3.24f1**. It is not an official Unity patch release. Exactly **one of 293 original package files** changed: `Runtime/UDPNetworkInterface.cs`. All original notices/licenses and metadata remain. A patch note and its Unity metadata are added. The editor installation and old Meeps project are untouched. [Exact diff](evidence/rejoin-recovery-2026-09-24/transport-patch-1.diff), [verified provenance](evidence/rejoin-recovery-2026-09-24/transport-provenance.json), [original file hashes](evidence/rejoin-recovery-2026-09-24/upstream-transport-2.7.4-files.json).

The package lives at `Unity/FamilyPlayset/Packages/com.unity.transport`; the lockfile identifies it as embedded. Review this small patch whenever upgrading Unity Transport. Retire it when an upstream version fixes the ownership paths and passes the same regression tests. Do not silently revert to a registry package or blindly reapply the diff across versions.

## Movement regression found during qualification

One build-66 delayed-motion test exceeded the unchanged p95 speed limit: **427.77 units/s** versus a **420** limit. Its remote avatar moved on **87%** of steady-walk frames. The trace recorded **21 paused frames exactly at the newest available position** out of 161 frame pairs. This is consistent with the renderer exhausting its interpolation history. A repeat passed narrowly at 413.33 units/s and still 87%; a fresh run of old build 63 measured 90.7%. Those short runs vary with packet/frame timing and are retained, not discarded in favor of the best result. [Failure](evidence/rejoin-recovery-2026-09-24/motion-66-first-failed.json), [repeat](evidence/rejoin-recovery-2026-09-24/motion-66-repeat.json), [old-build comparison](evidence/rejoin-recovery-2026-09-24/motion-63-comparison.json), [trace summary](evidence/rejoin-recovery-2026-09-24/marginal-buffer-trace.json).

Build **68** retains the same transport fix and increases the remote-avatar/held-prop interpolation delay from **120 to 180 ms**. This gives the tested packet delay, jitter and missed samples more room. Own-player visual anticipation stays immediate; authoritative walking, inventory rules and save formats are unchanged. This adds 60 ms of presentation delay for other players. It is an initial measured setting, not a universal optimum for every Wi-Fi network. Buffering history trades latency for smoother rendering, as described in the earlier [movement research](g3-smooth-movement-2026-09-24.html) and [Fiedler's interpolation explanation](https://gafferongames.com/post/snapshot_interpolation/).

## What this does and does not prove

All automated network runs use separate native Windows processes and isolated loopback worlds with test credentials. They do not use or reset the family's preview save. During the eight build-66 crash cycles, the same server PID and epoch stayed active and the surviving clients committed **148 fresh commands**. Rejoining clients were explicitly relaunched by the test harness; the approximately 3.6–3.7 second measurements include process launch and presentation readiness, and are not a network-only latency benchmark.

This fix is not automatic host switching. Losing the authority itself still stops this prototype's session; the tested restart restores its checkpoint and clears stale holds. The intended home flow remains automatic connection to the PC, with required iPad hosting and recovery developed in their planned phases. No firewall rules, public endpoints, router settings or phone installations were changed here.

The embedded native transport change still needs **iOS/Android IL2CPP builds and physical mixed-device qualification**, including the older iPad's performance and repeated background/foreground/disconnect behavior. Existing solo iPad build 56 is unchanged. Full-network impairment, long-duration play and the future larger world's load remain separate gates. G1/G2/G3 are not declared complete by these PC results.
