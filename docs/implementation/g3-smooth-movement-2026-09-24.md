## What the current code actually did

Inspection of build-58 source found direct assignment of remote avatar position whenever a snapshot arrived. Walking also used the same one-in-flight acknowledgement queue as item transactions, with a 50 ms send gate, waiting for the previous response. Each accepted step generated a receipt, serialized the whole world, and synchronously flushed a checkpoint to disk. The position was then sent twice as response/broadcast in reliable state messages. These are confirmed code behaviors, not measurements of a particular iPad or an inferred slow router. The test-only 250 ms acknowledgement delay is not enabled in the user's interactive preview.

## Source-backed findings

- **Render between snapshots.** Fiedler demonstrates how irregular packet arrivals cause visible jumps even with a high send rate. Buffering timestamped snapshots lets the renderer interpolate between known states; it trades a small amount of presentation delay for steadier motion. Lost superseded snapshots need not block later ones. Buffer sizing depends on send rate, jitter and loss; the article's example numbers are not universal defaults for this game. [Snapshot Interpolation — Glenn Fiedler](https://gafferongames.com/post/snapshot_interpolation/).
- **Separate simulation rate from rendering.** Gambetta explains a server that advances at a regular timestep instead of simulating separately on each arriving request. Other players can be rendered along the received trajectory between authoritative updates. For this game's slow, noncompetitive walking, a short visual buffer is a reasonable engineering choice; it does not require MMO-scale infrastructure. [Entity interpolation](https://www.gabrielgambetta.com/entity-interpolation.html).
- **Own-player responsiveness is a separate problem.** Full prediction/reconciliation retains numbered inputs and replays unacknowledged work after correction. Our first walking-only implementation uses simpler local visual anticipation and bounded correction, not a complete rollback/replay simulation. Inventory/water transfers remain server-confirmed. [Prediction and reconciliation](https://www.gabrielgambetta.com/client-side-prediction-server-reconciliation.html).
- **Unity already supports these patterns, but does not supply our game's complete rules.** NGO's anticipation distinguishes visual state from authoritative state, including handling stale responses and smoothing corrections. Its documentation explicitly distinguishes anticipation from full prediction/reconciliation. Our existing 2D canvas has no NetworkObject hierarchy; adding NetworkTransform alone would neither remove the movement acknowledgement queue nor stop per-step saving. The pinned NGO/UTP packages stay installed. The public 2.13 documentation currently identifies patch 2.13.3; this project remains pinned to 2.13.2. [Unity client anticipation](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/advanced-topics/client-anticipation.html).
- **Reliable delivery has costs.** Reliable packets can hold later messages behind loss/retransmission. Replaceable movement samples are suitable for sequenced unreliable delivery, while state-changing transactions require their reliable, idempotent path. Unity's transport documentation describes these pipeline tradeoffs. Our movement packets are complete compact positions, not dependent deltas, and are checked against a 1,200-byte application budget. [Unity Transport pipelines](https://docs.unity3d.com/Packages/com.unity.transport@2.7/manual/pipelines-usage.html).
- **Use consistent clocks and test bad conditions.** NGO exposes local/server network time and tick scheduling. Use double-precision time for the interpolation timeline. Qualification needs jitter, delay and packet loss as well as an ideal local connection. Unity's Network Simulator is an available broader testing tool; the initial custom fixture below only impairs received movement snapshots, which is a narrower test. [Network time and ticks](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/advanced-topics/networktime-ticks.html), [Network Simulator](https://docs.unity3d.com/Packages/com.unity.multiplayer.tools@2.2/manual/network-simulator.html).

## Chosen first implementation

| Part | Initial setting / reason |
| --- | --- |
| Server walking | Fixed 30 Hz; normalized direction or destination at 210 floor units/second; bounded catch-up |
| Input and position stream | Approximately 20 Hz, sequenced, no waiting for item acknowledgements; authenticated connection, area and visit checked |
| Remote avatars | Timestamp buffer, 120 ms behind the client's synchronized server clock; interpolate each rendered frame; hold the last known point during a long outage. Samples are stamped at the completed simulation step, avoiding artificial speed fluctuation when 30 Hz simulation is sampled at 20 Hz. |
| Own avatar | Immediate visual walking, acknowledgement-aware correction; pause anticipation after stale incoming state; authority still sets actual position |
| Stops | Reliable stop intent, repeated latest input, plus a 400 ms authority watchdog if input disappears |
| Area changes | Clear old walk intent; reset interpolation on a different area/visit; reject delayed input from earlier visits |
| Shared items | Exclusive holders and confirmed fill/pour/drop remain transactional; remote held-item presentation also interpolates accepted drag positions |
| Disk persistence | Coalesce walking checkpoints to approximately once/second while moving, save settled positions and graceful exits, and include current positions in every durable item transaction |
| Render rate | Windows shared preview targets 60 FPS; existing mobile targets are unchanged pending device measurements |

A hard server process kill during uninterrupted walking can lose up to roughly one checkpoint interval of **position**, plus scheduling/disk time. Completed item transactions retain their existing immediate checkpoint contract. This tradeoff must remain explicit; calling every transient movement packet “durably saved” would be incorrect. Movement does not increment the inventory transaction revision or create durable action receipts, so a continuously walking sibling cannot cause endless revision conflicts for a bucket pickup.

These rates and buffers are our initial measured-test candidates, not claims of ideal values for all devices/networks. Four-player iPad/Android profiling, sustained heat/battery checks, wider network impairment, obstacle/navigation collision rules and required iPad-host recovery are later qualification work. The existing intermittent initial join/rejoin stall has not been declared fixed by this movement change.

## Four players are the supported design target

The same authority simulates all four profiles. Every client sends its own latest walking intent; each movement snapshot contains all four current positions. One client's frame rate or acknowledgement delay does not choose another player's walking speed. Per-player sequence numbers and visit numbers prevent an old input from undoing a newer stop or driving a character after travel. Bucket ownership, water, activities and room changes retain server-confirmed rules. The second player's view does not pause when the first player changes areas.

Sending four small positions about 20 times/second is a reasonable initial budget for this family game. The enforced 1,200-byte application-payload ceiling gives an upper bound of about **96 KB/second** for movement snapshot payload sent by one server to four clients (1,200 × 20 × 4), excluding transport headers, inputs and transactions. That is a ceiling calculation, not a bandwidth measurement. The actual four-avatar message is smaller. Increasing send rate alone would not fix irregular arrival times, blocked item queues or slow rendering; the implementation addresses each separately.

Unity's tools support multiplayer testing and network simulation, including four-player local iteration. Here we use separate native Windows clients so the tests include their real UI and built player code. Four local processes still do not represent four different mobile processors or Wi-Fi radios. [Unity networking tools](https://docs.unity.com/en-us/multiplayer/netcode/networking-utilities).

The proposed mobile acceptance sequence is: both iPads plus Android and iPhone on one server; all four in one busy room, then split across rooms; concurrent walking, dragging, watering and travel; one player backgrounds/closes while the others continue; repeat with controlled delay, jitter, loss and an interrupted connection. Measure frame-time percentiles, render stalls, snapshot age, correction distance, bytes/second, memory and garbage collection. Start with stable 30 FPS on the older iPad (about 33.3 ms/frame); only raise the target when sustained device measurements support it. Use device profiling builds to find costs, then repeat behavioral/performance checks on the intended release build. These are acceptance plans, not completed mobile results. [Unity 6.3 target-device profiling](https://docs.unity3d.com/6000.3/Documentation/Manual/profiling-target-device.html).

For the eventual larger playset, load/render only the current area's art, pool frequently reused effects, avoid allocations in continuous movement, and send detailed object updates only to interested areas while preserving shared server state. Those are later workload controls, not a restriction forcing four players to stay together. The current ten-prop prototype still uses full reliable state snapshots for transactions. Required iPad hosting, automatic joining and host switching remain separate implementation gates. No networking technique can guarantee uninterrupted shared authority through every disconnection; recovery must be measured separately from smooth rendering.
