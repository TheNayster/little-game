## Proposal: layout and interaction

Open a local close camera view of the existing Daycare sandpit; recommend retaining the Daycare world/participation domain rather than inventing a new network zone. Creation remains server-owned. Local framing returns on Leave without clearing pieces. A warm rim, garden greenery, teacher and edge avatars retain the setting. Illustrative mockup art is composition evidence only; the approved cast and daycare illustration style remain the production reference.

- **Tablet:** central pit occupies roughly the middle two-thirds of the screen width; slim top row has Leave left and optional help right. Four avatars stand at rim anchors. A bottom shelf has Build/Decorate picture tabs, with one four-card tray visible. A compact active bucket/next-tool panel sits beside the pit in its own clear region; selecting a farther piece pans locally so it remains visible.
- **Narrow phone:** full-width pit above a compact bottom shelf; next tool moves to the shelf's trailing area. Use four visible cards or a clamped horizontal picture tray with a visible next card, keeping hit size. Collapse text, never shrink essential targets to fit. No joystick/character-chooser overlap. Placement has a picture check/cancel strip and a translucent ghost; no permanent duplicate action row.
- **Selection:** numbered/shape player badge plus outline and pointer arrow; color is supplemental. Each client has one active piece. A small shared contributor badge may identify the latest accepted worker; it is feedback, not a permanent ownership lock. Avatar bodies cannot intercept piece/tool targets.
- **Tools:** filled scoop pips plus the actual rising bucket surface; wet tint plus droplet icon; one obvious next tool (shovel → can → Tip). Water-before-fill stays allowed through a secondary picture control. Early Tip recovery lives in the bucket interaction, not a text error. Help shows the current action without moving another player or delaying play.
- **Decorations/play:** choose a decoration picture, see valid sockets on the selected built piece, tap a generous socket (or accept the suggested socket). Flag and shell remain visible together. Doors/windows use front-face sockets; flag uses top; pebbles/shells use ledges/base. Tap flag/door/toy for short reactions. Build remains available after every reveal.

## Technical contract and migration proposal

Keep `SoloAction.Sandpit` and existing submission/receipt/revision plumbing if their 128-character target/value bounds suffice. Capture creation epoch + stable piece ID at input time, and captured piece version for destructive edits; retries change only expected world revision. Placement commands carry exact proposed shape/cell/orientation, never an automatically chosen fallback after a retry. An overlapping placement rejected on rebasing returns to local preview. Authority owns bounds/occupancy, fill/recovery, attachments and reset vote. Client owns mould choice, selection, pending tap count, preview, camera, tool hints and short effects.

Use saved monotonic piece IDs/serial; do not reuse a deleted ID within an epoch. Local selection invalidates cleanly when its target is removed or epoch changes. Existing four-element observers must become bounded ID-keyed observers; baseline current data on late join/reconnect, skip unobserved transient history, and clear local pending intent on Leave/menu/pause/travel/disconnect. Immediate pointer/tool nudge is allowed before acknowledgment, but a built piece/attached decoration must follow accepted authoritative data.

Derive one reachable rim/work point per piece footprint using the existing bounded approach pattern. Approach once when selecting a different work site; shovel/can/Tip must share that point, never send the child between source props. Tap cues and retained Scoop intent stay immediate while authority still validates reach. Measure actual approach delay in S2; if rim paths remain noticeably slow, propose the narrow interaction-radius/framing change before weakening reach validation. Do not fake success while the avatar is walking or silently allow arbitrary distant commands.

Preserve the legacy lesson's four coordinates as migrated footprints; do not silently move an existing castle merely to fit a new snap grid. Recommend a small legacy-coordinate allowance within the pit layout helper, with new placements checking against those footprints. If enlarged/centred presentation requires coordinate conversion, use a view transform; moving saved world content is a separate decision. Keep original capacity per legacy piece; new pieces use the approved consistent capacity. Legacy creator identity is unknown: mark it as shared legacy work, never invent an owner; editing follows the approved family/parent route. Migrate single Flag/Shell to one compatible attachment; neither invent a second decoration nor drop the original. Convert completed phase to continued play while retaining epoch/cast; do not interpret old phase as permission to clear.
